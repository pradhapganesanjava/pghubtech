Approach — unbounded knapsack (max value within a budget)

Time is the capacity (k minutes), each query type is a reusable item with weight time[i] and value revenue[i]. Maximize value with repetition allowed.

dp = [0] * (k + 1)            # dp[t] = max revenue in <= t minutes
choice = [-1] * (k + 1)       # which type we took to reach dp[t] (for reconstruction)
for t in range(1, k + 1):
    for i in range(n):
        if time[i] <= t and dp[t - time[i]] + revenue[i] > dp[t]:
            dp[t] = dp[t - time[i]] + revenue[i]
            choice[t] = i
# reconstruct the selected query types
t, picks = k, []
while t > 0 and choice[t] != -1:
    picks.append(choice[t]); t -= time[choice[t]]
return dp[k], picks            # max revenue + which types

O(n·k) time, O(k) space. The choice[] array recovers which query type(s) were run. This is the max-value twin of Coin Change (#322) — same loop order (capacity outer, items inner) lets each type repeat.

Variants: if each type may run at most once, it's 0/1 knapsack (iterate capacity descending — #416/#494). If you must pick exactly ONE type and run it the whole k minutes, it degenerates to max over i of floor(k/time[i]) · revenue[i] — no DP.

Follow-up trio

  • Multi-threaded — for a fixed t, the max over the n query types is a parallel reduction; or shard the capacity range across threads with care at boundaries. The dp is sequential in t, so pipeline by capacity blocks.
  • Streaming — query types are added over time: dp is monotone in the item set, so on a new type i just relax dp[t] = max(dp[t], dp[t-time[i]] + rev[i]) for t ascending — an incremental O(k) update, no full rebuild.
  • O(1)-space — the dp is already a single O(k) array (rolling); revenue-only (no reconstruction) needs just that array. The choice[] adds O(k) only if you must report the types.
