Approaches

1) Prefix / rolling hash — O(n + Σm)

Precompute a polynomial prefix hash of the ingredient list so any window's fingerprint is O(1). For each recipe, hash it once and compare against the matching-length windows (Rabin-Karp); verify on a hash hit to avoid collisions. (Enumerating all contiguous subsequences and bucketing them is the O(n²) brute force; the prefix hash makes each query cheap.)

# text = ingredient list, queries = recipes
H = prefix_hash(text); P = pow_table(B)
def window_hash(l, r):                 # hash of text[l..r] in O(1)
    return (H[r+1] - H[l] * P[r-l+1]) % MOD
def matches(recipe):
    m = len(recipe); rh = hash(recipe)
    return any(window_hash(i, i+m-1) == rh and text[i:i+m] == recipe
               for i in range(len(text) - m + 1))

2) Follow-up 1 — O(1) extra space (two-pointer / sliding window)

For each recipe of length m, slide a window over the list and compare element by element; reset on mismatch. O(n·m) time but only O(1) extra space (no hash tables) — this is the naive strStr scan.

3) Follow-up 2 — streaming (state machine)

When ingredients arrive as a large stream, build a matching automaton and feed the stream through it in one pass: KMP failure-function automaton per recipe, or — for many recipes at once — Aho-Corasick (a trie of all recipes + failure links), which matches every recipe in O(stream + total recipe length + #matches).

Follow-up trio

  • Multi-threaded — recipes are independent: shard them across threads (each runs its own KMP/Rabin-Karp over the shared read-only list), or build one Aho-Corasick automaton and split the stream into chunks with overlap = max recipe length.
  • Streaming — Aho-Corasick / KMP automaton consumes the ingredient stream online; emit a recipe the instant its accept state is hit (see Follow-up 2).
  • O(1)-space — the two-pointer scan (Follow-up 1) uses O(1) beyond the inputs; rolling hash trades O(1) space for O(n) speed.
