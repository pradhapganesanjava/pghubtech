Simple Introduction

What Kubernetes is, what problem it solves, and why it matters

Kubernetes (K8s) is an open-source container orchestration platform originally built at Google and donated to the CNCF in 2014. It automates the deployment, scaling, self-healing, and networking of containerized applications across clusters of machines. The layer model it operates on is: Physical Hardware → Linux OS Kernel → Container Runtime (as kernel processes) → Containers (isolated application environments) — Kubernetes sits above all these layers and treats your entire fleet as a single programmable computer.

The core insight is that containers package an application together with all its dependencies (shared libs, config, runtime) into a portable, reproducible unit. Kubernetes then decides where to run those containers, ensures they stay running, handles traffic routing, and manages secrets and configuration — all driven by declarative YAML that describes desired state rather than imperative scripts.

The Problem: "Works on My Machine"

Applications depend on specific OS library versions, environment variables, and runtime configurations. Without isolation, two apps can conflict on the same host. Deploying to production becomes fragile — the dev environment, CI, staging, and prod all differ subtly. Manual scaling and failure recovery don't scale.

The Solution: Containers + Orchestration

Containers bundle every dependency into a portable image (like a snapshot of a full OS filesystem). Kubernetes then runs hundreds of those containers across many machines, replaces crashed ones automatically, load-balances traffic, rolls out updates with zero downtime, and manages secrets — all from a single YAML source of truth.

Key One-Liners

Pod: one or more containers sharing a network namespace.
Node: the machine (VM or bare-metal) that runs pods.
Deployment: declares how many pod replicas to maintain.
Service: stable DNS name + load balancer in front of pods.
Namespace: virtual cluster — like Python's venv, but for K8s resources.

Key insight: Kubernetes is fundamentally a desired-state reconciler — you declare what you want (3 replicas of this image), and K8s continuously works to make reality match that declaration, even when nodes crash or traffic spikes.

The City Infrastructure Analogy

Kubernetes concepts mapped to how a city manages buildings, workers, and utilities

Imagine running a large city where the city council (Control Plane) decides where to build things, the city districts (Nodes) are the actual land, and containers are the individual buildings that house businesses. Services are the road addresses, and ConfigMaps are the city's zoning laws. The city self-heals: if a building collapses, the council immediately orders a replacement built on available land.

Key Statements

The most important truths about Kubernetes, one at a time
1
Kubernetes is a desired-state reconciler, not a command executor. You declare what you want in YAML; K8s continuously compares actual state to desired state and corrects any drift — forever.
2
Containers solve dependency portability the same way Python venv solves package isolation. Both wrap a runtime environment so the same code runs identically on any host, eliminating host-level conflicts.
3
The stack layers are: Hardware → Linux Kernel → Container Runtime → Container. Kubernetes orchestrates at the container layer and above; it doesn't replace the OS — it treats the OS as a stable substrate.
4
A Pod, not a container, is the smallest deployable unit. Pods can group tightly-coupled containers (e.g., an app + a log-shipper sidecar) that share a network namespace and lifecycle.
5
etcd is the single source of truth for all cluster state. If etcd is healthy, the cluster can fully reconstruct itself from it. Every object — pods, services, secrets — lives there as JSON.
6
Services decouple traffic from pod IPs. Pod IPs are ephemeral (change on restart); Services provide a stable ClusterIP backed by iptables or IPVS rules that auto-update as pods come and go.
7
Kubernetes does not build or push images. It only pulls images from a registry (Docker Hub, ECR, GCR). Building images is the CI system's job, not K8s's.
8
Namespaces provide soft multi-tenancy. They scope resource names, RBAC rules, and NetworkPolicies — but they do not provide kernel-level isolation between tenants (for that, use separate clusters or gVisor/Kata containers).
9
Rolling updates and rollbacks are first-class operations. A Deployment tracks revision history; kubectl rollout undo reverts the live workload to any previous ReplicaSet in seconds.
10
Kubernetes is extensible by design. Custom Resource Definitions (CRDs) let you define new object types (Kafka topics, ML training jobs, database clusters) that K8s manages with the same reconciliation machinery.

Core Components

Every major building block, what it does, and how to declare it

Pod — The Atomic Unit

One or more containers co-located on the same Node, sharing a network namespace (same IP, same localhost) and optional shared volumes. Pods are ephemeral — never update a running pod; instead, replace it via a controller.

apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
spec:
  containers:
  - name: app
    image: my-app:1.2.3       # immutable image tag recommended
    ports:
    - containerPort: 8080
    resources:
      requests: { cpu: "100m", memory: "128Mi" }
      limits:   { cpu: "500m", memory: "512Mi" }

Deployment — Declarative Pod Management

Wraps a ReplicaSet to maintain N pod replicas at all times. Handles rolling updates, rollbacks, and scaling. This is how you run stateless workloads in production — never create bare pods.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels: { app: my-app }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:
    metadata:
      labels: { app: my-app }
    spec:
      containers:
      - name: app
        image: my-app:1.2.3

Service — Stable Network Endpoint

Provides a permanent ClusterIP (and optionally a LoadBalancer IP) that routes to any pod matching its label selector. kube-proxy maintains iptables rules so traffic always reaches a live pod, even as pods restart.

apiVersion: v1
kind: Service
metadata:
  name: my-app-svc
spec:
  selector:
    app: my-app           # routes to pods with this label
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP         # or LoadBalancer for external access

ConfigMap & Secret — Dependency Configuration

ConfigMaps inject non-sensitive config (feature flags, URLs) as env vars or mounted files. Secrets are base64-encoded (optionally encrypted at rest) for credentials. Both decouple configuration from the image — the same image runs in dev, staging, and prod with different injected values.

# ConfigMap: environment-specific settings
apiVersion: v1
kind: ConfigMap
metadata: { name: app-config }
data:
  DATABASE_URL: "postgres://db:5432/mydb"
  LOG_LEVEL: "info"

# Secret: sensitive values
apiVersion: v1
kind: Secret
metadata: { name: app-secret }
stringData:
  DB_PASSWORD: "s3cr3t"   # K8s base64-encodes this

Namespace — Virtual Cluster (the "venv" of K8s)

Namespaces partition one physical cluster into isolated logical environments — exactly as Python's venv isolates packages per project. You can have dev, staging, and prod namespaces on one cluster, each with their own resource quotas and RBAC rules. Cross-namespace communication uses the DNS form svc.namespace.svc.cluster.local.

apiVersion: v1
kind: Namespace
metadata:
  name: production
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: prod-quota
  namespace: production
spec:
  hard:
    pods: "50"
    requests.cpu: "10"
    requests.memory: "20Gi"

Pod Lifecycle & Scheduling Flow

From kubectl apply to a running container — every step the cluster takes
Full pod creation lifecycle — from YAML to running container on a node
① kubectl apply -f deployment.yaml
→
CLI serializes YAML to JSON, sends HTTP POST to API Server
② API Server validates & persists
→
Auth/RBAC check, schema validation, then writes Deployment object to etcd
③ Deployment Controller watches
→
Controller Manager detects new Deployment; creates a ReplicaSet object in etcd
④ ReplicaSet Controller watches
→
Detects ReplicaSet with 0 actual pods; creates Pod objects in etcd (status: Pending)
⑤ Scheduler watches for Pending Pods
→
Scores each Node (CPU, memory, affinity, taints); binds pod to best Node via API Server
⑥ kubelet on target Node watches
→
Sees pod bound to its Node; calls container runtime (containerd) to pull image
⑦ Container image pulled from registry
→
containerd pulls layers over HTTPS, verifies digests, unpacks to overlay filesystem
⑧ Container started via OCI runtime (runc)
→
Linux namespaces + cgroups created; container PID 1 launched; pod IP assigned by CNI plugin
⑨ Probes begin
→
startupProbe runs first; then livenessProbe (restart if fails) + readinessProbe (remove from Service endpoints if fails)
⑩ Pod status → Running
→
kubelet updates pod status in etcd; kube-proxy adds pod IP to Service's iptables rules
⑪ Traffic reaches the pod
→
Service ClusterIP → iptables DNAT → pod IP; DNS resolves service name via CoreDNS
⑫ Self-healing: pod crashes
→
kubelet reports crash → ReplicaSet Controller detects missing pod → creates replacement → loop restarts at ⑤
Automatic steps: Steps ③ through ⑫ are all automatic after you run kubectl apply. The only manual step is writing the YAML and pushing the image. Everything else is K8s reconciliation loops running continuously.

Control Plane Internals

How the brain of the cluster works — API server, etcd, controllers, scheduler
Core truth: Every K8s component — controllers, scheduler, kubelet — communicates exclusively through the API Server. No component writes directly to etcd except the API Server. This makes the architecture auditable and extensible.
Component 1

kube-apiserver

The only entry point to cluster state. Validates all requests, enforces RBAC, serves the REST API, and fan-outs watch events to all interested controllers.

# All K8s operations are HTTP REST
GET  /api/v1/namespaces/default/pods
POST /apis/apps/v1/deployments
WATCH /api/v1/pods?watch=true  # long-poll SSE stream
Component 2

etcd

Distributed key-value store using the Raft consensus algorithm. All cluster state — every pod, service, secret, RBAC rule — persists here as JSON under /registry/ keys. Losing etcd without a backup loses the entire cluster.

# Keys K8s writes into etcd
/registry/pods/default/my-app-abc12
/registry/services/default/my-app-svc
/registry/deployments/apps/default/my-app
/registry/secrets/default/app-secret
Component 3

kube-scheduler

Watches for unscheduled pods (no nodeName set). Runs Filter (hard constraints: node has enough CPU/memory, no taints) then Score (soft ranking: spreading, affinity). Writes the chosen node back to the pod spec.

# Scheduler plugins chain
Filter → NodeResourcesFit
Filter → NodeAffinity
Filter → TaintToleration
Score  → BalancedAllocation
Score  → InterPodAffinity
→ Bind: write pod.spec.nodeName
Component 4

Controller Manager

A single binary running dozens of reconciliation loops: Deployment, ReplicaSet, Node, Job, CronJob controllers. Each watches a specific resource type and acts when actual state diverges from desired state — the engine of K8s's self-healing.

# Controller reconcile loop (pseudocode)
for ever:
  actual = get_current_pods(selector)
  desired = deployment.spec.replicas
  if len(actual) < desired:
    create_pod()
  elif len(actual) > desired:
    delete_pod()

kubelet — The Node Agent

kubelet runs on every worker node. It watches the API Server for pods scheduled to its node, then drives the container runtime (via CRI — Container Runtime Interface) to start/stop containers. It also runs probes and reports pod status back to the API Server.

# kubelet flow on a node
1. Watch API Server: "any pods for me?"
2. Pod assigned → pull image via containerd (CRI gRPC)
3. Set up Pod sandbox: network namespace (via CNI), cgroups (via CRI)
4. Start containers: runc creates Linux namespaces
   - pid namespace (isolated process tree)
   - net namespace (own IP stack, assigned by CNI)
   - mnt namespace (overlay filesystem from image layers)
   - uts namespace (hostname = pod name)
5. Run probes (HTTP GET / exec / TCP)
6. Report status every 10s to API Server via heartbeat

Service Routing & Traffic Dispatch

How a request finds the right pod — DNS, iptables, Ingress, and load balancing

ClusterIP + kube-proxy (iptables mode)

kube-proxy watches Service and Endpoints objects. For each Service, it programs iptables DNAT rules on every node: traffic to ClusterIP:port is randomly load-balanced across healthy pod IPs. Pod IPs are removed from Endpoints when readinessProbe fails.

# Effective iptables rule created by kube-proxy
-A KUBE-SERVICES -d 10.96.0.50/32 -p tcp --dport 80 \
  -j KUBE-SVC-XYZ

# KUBE-SVC-XYZ randomly selects a pod
-A KUBE-SVC-XYZ -m statistic --mode random \
  --probability 0.33 -j KUBE-SEP-POD1
-A KUBE-SVC-XYZ -m statistic --mode random \
  --probability 0.50 -j KUBE-SEP-POD2
-A KUBE-SVC-XYZ -j KUBE-SEP-POD3

CoreDNS — Service Discovery

Every pod gets CoreDNS as its DNS server (configured via /etc/resolv.conf injected at pod startup). Service names resolve to their ClusterIP automatically. Pattern: svc-name.namespace.svc.cluster.local

# DNS names K8s registers automatically
my-app-svc                    # same namespace
my-app-svc.production         # cross-namespace short form
my-app-svc.production.svc.cluster.local  # FQDN

# Headless service (no ClusterIP) returns pod IPs directly
spec:
  clusterIP: None   # DNS → individual pod IPs (for StatefulSets)

Ingress — External HTTP Routing

Ingress is an L7 (HTTP/HTTPS) routing layer sitting in front of Services. An Ingress Controller (nginx, Traefik, AWS ALB Controller) watches Ingress objects and configures the actual reverse proxy. Routes are matched by host and path; TLS termination and certificate management (via cert-manager) happen here.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  tls:
  - hosts: ["app.example.com"]
    secretName: app-tls
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service: { name: api-svc, port: { number: 80 } }
      - path: /
        pathType: Prefix
        backend:
          service: { name: frontend-svc, port: { number: 80 } }

Deep Technical Aspects

Linux primitives, network internals, storage, security, and performance details

Linux Namespaces (Isolation Layer)

  • Containers are Linux processes wrapped in 7 namespaces: pid, net, mnt, uts, ipc, user, cgroup
  • pid namespace: container's PID 1 is actually PID ~50,000 on the host
  • net namespace: each pod gets its own eth0, loopback, and routing table
  • mnt namespace: overlay filesystem — read-only image layers + writable top layer
  • user namespace: (optional) maps root inside container to unprivileged UID on host
  • Namespaces are NOT VMs — the kernel is shared; a kernel exploit can escape all containers
  • Kata Containers / gVisor add a hypervisor layer for stronger isolation

cgroups (Resource Limits)

  • Control Groups v2 (cgroups2) enforces CPU and memory limits declared in pod spec
  • requests = guaranteed reservation used by the scheduler for bin-packing
  • limits = enforcement ceiling — CPU throttled by CFS bandwidth; memory OOM-killed
  • BestEffort pods (no requests/limits) are killed first under node memory pressure
  • Burstable pods (requests < limits) can burst but can be throttled
  • Guaranteed pods (requests == limits) get highest QoS class — rarely evicted
  • CPU throttling is the most common cause of latency spikes in K8s workloads

Container Networking (CNI)

  • Every pod gets a unique routable IP from the pod CIDR range (e.g. 10.244.0.0/16)
  • CNI plugin creates a veth pair: one end in pod's net namespace, one in host bridge
  • Pod-to-pod on same node: traffic through host bridge (kernel; sub-microsecond)
  • Pod-to-pod cross-node: overlay (VXLAN/WireGuard) or BGP routing depending on CNI
  • Popular CNIs: Calico (BGP, NetworkPolicy), Flannel (VXLAN), Cilium (eBPF, L7 policy)
  • NetworkPolicy objects are K8s-native firewall rules implemented by the CNI, not kube-proxy
  • Cilium replaces iptables entirely with eBPF programs for better observability and performance

Persistent Storage (CSI)

  • Container filesystems are ephemeral — destroyed when pod dies unless using Volumes
  • PersistentVolume (PV) is a cluster-scoped storage resource; PVC is a pod's claim on one
  • StorageClass enables dynamic provisioning: PVC creates EBS/GCS disk automatically
  • Access modes: ReadWriteOnce (one node), ReadOnlyMany (many nodes), ReadWriteMany (NFS/EFS)
  • StatefulSets provide stable pod identity + per-pod PVCs (for databases, Kafka brokers)
  • CSI (Container Storage Interface) drivers are out-of-tree plugins — no kernel recompilation
  • emptyDir volumes are ephemeral, RAM-backed options for sharing data between sidecar containers in a pod

RBAC & Security Model

  • Every request to the API Server passes through: Authentication → Authorization (RBAC) → Admission Control
  • ServiceAccount = identity for pods; token automounted into /var/run/secrets/kubernetes.io/serviceaccount
  • Role (namespace-scoped) and ClusterRole (global) define permissions as verb+resource tuples
  • RoleBinding attaches a Role to a subject (User, Group, ServiceAccount)
  • Admission webhooks (MutatingAdmissionWebhook, ValidatingAdmissionWebhook) run after auth for policy enforcement (e.g. OPA Gatekeeper)
  • PodSecurity Standards (baseline, restricted) restrict privileged containers at the namespace level
  • Secrets are only base64-encoded by default — enable etcd encryption at rest for real security

Horizontal Pod Autoscaler (HPA)

  • HPA queries the Metrics Server (or custom metrics API) every 15s to compute desired replicas
  • Formula: desiredReplicas = ceil(currentReplicas × (currentMetric / targetMetric))
  • Supports CPU, memory, and custom metrics (e.g., Kafka consumer lag, RPS)
  • Scale-up is fast (immediate); scale-down has a 5-minute stabilization window by default to prevent flapping
  • Vertical Pod Autoscaler (VPA) adjusts CPU/memory requests in-place
  • KEDA (Kubernetes Event-Driven Autoscaling) extends HPA to 60+ event sources
  • Cluster Autoscaler adds/removes Nodes when pods can't be scheduled or nodes are underutilized

Image Layers & Dependency Portability

  • A container image is a stack of read-only layers (tarballs) identified by SHA256 digest
  • Layers are cached on each node — only changed layers are pulled on image updates
  • Base layer (e.g. python:3.12-slim) contains OS libs; app layer adds your code
  • Each layer is immutable — identical to the byte on any host anywhere in the world
  • This is the core portability guarantee: same SHA256 → identical behavior on dev, CI, prod
  • OCI (Open Container Initiative) spec defines image format — not Docker-proprietary
  • Multi-stage builds reduce final image size by discarding build tools from the runtime layer

etcd & Consistency Guarantees

  • etcd uses Raft consensus: a write is committed only after a majority quorum acknowledges it
  • 3-node etcd cluster tolerates 1 node failure; 5-node tolerates 2
  • API Server uses optimistic concurrency: every object has a resourceVersion; updates rejected if stale
  • Watch streams are served from etcd's event history — controllers reconnect and replay missed events
  • etcd write latency is the bottleneck for large clusters; Kubernetes recommends <10ms P99 disk latency for etcd nodes
  • etcd snapshots are the backup mechanism — restore by loading snapshot into a new etcd cluster
  • Large secrets should use external secret stores (Vault, AWS Secrets Manager) via CSI driver to avoid bloating etcd

Frequently Asked Questions

Common questions — click to expand
Q   What is the difference between a container and a Pod? ▼
A container is the running process isolated by Linux namespaces and cgroups. A Pod is Kubernetes' smallest deployable unit — it wraps one or more containers that share the same network namespace (same IP address, same localhost) and optionally share volumes. You almost never create bare containers in K8s; you create Pods (usually via a Deployment). Sidecar patterns (log-shipper, service mesh proxy) run as additional containers within the same Pod alongside the main app container.
Q   How does Kubernetes solve dependency management and portability? ▼
Container images bundle every dependency — OS libraries, runtime, config files, binaries — into an immutable, content-addressed (SHA256) artifact. This is the same principle as Python's venv, which isolates Python packages per project, but applied to the entire OS-level dependency tree. Because the image is identical on every host (same digest = same bytes), you eliminate "works on my machine" problems entirely. Kubernetes then manages where and how many copies of that image run, but the dependency isolation is provided by the container image itself.
Q   What is the layer model from hardware to application in Kubernetes? ▼
Hardware (physical CPUs, RAM, disks, NICs) → OS / Linux Kernel (manages hardware, provides system calls; Kubernetes uses cgroups and namespaces from this layer) → Container Runtime (containerd/CRI-O runs as OS processes; pulls images, creates namespaces/cgroups via runc) → Container (an isolated process with its own filesystem view, network stack, and process tree — like a lightweight VM without a separate kernel) → Kubernetes (orchestrates placement, health, scaling, and networking of containers across many nodes). Kubernetes does NOT replace any of the layers below it — it depends on the OS and container runtime being healthy.
Q   What is etcd and why is it so important? ▼
etcd is a distributed, strongly-consistent key-value store that holds all Kubernetes cluster state: every pod, service, secret, configmap, RBAC rule, and custom resource. It uses the Raft consensus algorithm so writes require a majority quorum — this guarantees no data loss on node failures up to (n-1)/2 failures. The API Server is the only component that reads and writes etcd directly. If you lose etcd without a backup, you lose the entire cluster's configuration (though running workloads on nodes may continue temporarily). Back up etcd snapshots regularly.
Q   How do Kubernetes Namespaces compare to Python virtual environments? ▼
The analogy is very direct. Python venv creates an isolated Python environment where installed packages don't conflict with other projects — same Python interpreter (OS), different package namespace. Kubernetes Namespaces create isolated logical environments within one cluster — same hardware and OS kernel, different K8s resource scopes. Both provide: (1) name isolation (same pod name can exist in dev and prod namespaces, just as same package name can exist in two venvs), (2) access boundaries (RBAC per namespace ≈ venv activation), (3) resource quotas (limit what each tenant can consume). Neither provides kernel-level isolation — for that you need separate clusters (K8s) or separate machines (venv gives OS-level isolation).
Q   How does Kubernetes handle zero-downtime deployments? ▼
Deployments use a rolling update strategy by default. With maxSurge: 1, maxUnavailable: 0, Kubernetes creates one new pod with the new image, waits for it to pass its readinessProbe, then terminates one old pod — and repeats until all pods are updated. Traffic is never routed to a pod that hasn't passed its readiness check (kube-proxy keeps it out of Service endpoints). If the new version's pods never become ready (crash loop or failing health check), the rollout stalls and old pods keep serving traffic. You can then run kubectl rollout undo to revert to the previous ReplicaSet in seconds.
Q   Does Kubernetes build Docker images? ▼
No. Kubernetes only pulls and runs pre-built images from a container registry. Building images (running docker build or buildkit) is entirely the CI/CD system's responsibility (GitHub Actions, Jenkins, Tekton, etc.). The workflow is: developer pushes code → CI builds the image, tags it (usually with the git commit SHA), and pushes to a registry (Docker Hub, ECR, GCR, Harbor) → you update your Deployment's image: field with the new tag → Kubernetes pulls the new image onto nodes and performs a rolling update.
Q   What happens when a Node (machine) goes down? ▼
The Node Controller in the Control Plane monitors node heartbeats (kubelet sends one every 10s). After ~40s of missed heartbeats, the node is marked NotReady. After a configurable tolerance period (default 5 minutes), the Node Controller evicts all pods from that node — it marks them for deletion. The ReplicaSet Controllers detect the missing pods and immediately schedule replacements on healthy nodes. If you had 3 replicas and 1 node dies holding 1 replica, K8s creates a new pod on a healthy node automatically. This is the core self-healing guarantee.
Q   What is the difference between liveness and readiness probes? ▼
Readiness probe: "Is this pod ready to serve traffic?" — if it fails, the pod is removed from Service Endpoints (no traffic sent) but the pod is NOT restarted. Use this for startup delays or temporary unavailability (cache warming, leader election). Liveness probe: "Is this pod still alive?" — if it fails consecutively (default: 3 times), kubelet kills and restarts the container. Use this to break out of deadlocks or hung processes that won't crash on their own. Startup probe: disables liveness/readiness until the app passes startup (used for slow-starting apps to avoid premature restarts). Rule of thumb: both probes should check real app health, not just "is the process running."
Q   When should I use StatefulSet instead of Deployment? ▼
Use a StatefulSet when your pods need: (1) stable, persistent hostnames (pod-0, pod-1 — never random IDs), (2) stable per-pod PersistentVolumes that survive pod restarts, or (3) ordered, graceful scaling and rolling updates (pod-0 must be ready before pod-1 starts). Classic use cases: databases (PostgreSQL, MySQL, Cassandra), message queues (Kafka brokers, RabbitMQ), ZooKeeper clusters. Use a Deployment for stateless workloads (APIs, web servers, workers) where any pod is interchangeable — this enables faster scaling and simpler operations. If you're tempted to run a database in K8s for the first time, start with a managed database (RDS, Cloud SQL) and only move to StatefulSet if you have specific requirements.
