Simple Introduction

What is gRPC and why do these files exist?

gRPC is a high-performance RPC framework from Google. It lets you call a function on a remote machine as if it were a local function call. Under the hood it uses Protocol Buffers for message encoding and HTTP/2 for transport.

The Problem It Solves

Without gRPC, two services talking over a network need to agree on: message format (JSON? XML?), serialization, connection management, retries, error codes, and interface contracts. gRPC handles all of it — you only define your service contract in a .proto file and everything else is generated.

The Three Files You Always See

your_service.proto — human-written contract defining messages and service methods.

your_service_pb2.py — auto-generated; handles message structure and serialization.

your_service_pb2_grpc.py — auto-generated; handles server/client plumbing.

One Sentence Each

pb2: "This is what data looks like."

pb2_grpc: "This is how data travels and who handles it."

Your Servicer: "This is the actual work that gets done."

Key insight: The .proto file is the single source of truth. Both the client (stub) and server (servicer base) are generated from the same file, which guarantees they are always in sync on method names and message shapes.

The Pizza Restaurant Analogy

Understand every component through a familiar real-world scenario

Imagine a pizza restaurant that takes orders over the phone. Every piece of gRPC maps perfectly to this scenario.

📋

Technical Concept

pb2.py — Message Definitions
The menu and order form. It defines what a pizza order looks like: size (small/medium/large), toppings (list), delivery address. Pure structure — no behavior, just shapes of data.

Technical Concept

pb2_grpc Stub — Client Side
The phone in your hand. It's pre-configured for the restaurant. When you dial and say "TakeOrder", the right buttons are pressed. You don't think about how the signal travels — you just speak.
📟

Technical Concept

pb2_grpc Servicer Base — Server Side
The blank answering machine at the restaurant. It knows to listen for calls. It knows calls can be for TakeOrder or CheckStatus. But it doesn't actually do anything — it's a template.

Technical Concept

Your Implemented Servicer
The actual cook who picks up the phone. You extended the blank answering machine and filled in real logic: store the order in the database, confirm delivery time, return an order ID.
🔧

Technical Concept

gRPC Framework + HTTP/2
The phone network and switchboard. Handles all wiring: packets, connections, retries, routing your call to the right extension. You never think about it — it just works.

Key Statements

The most important truths about gRPC, one at a time
1
pb2.py only cares about data shapes. It defines message classes (like Python dataclasses) and the logic to serialize them into bytes and deserialize bytes back. It knows nothing about servers, clients, or network.
2
pb2_grpc.py is the glue layer. It contains the Stub (client helper), the Servicer base class (server interface), and the registration function that wires them together. You never edit this file — protoc regenerates it.
3
The stub is not pre-wired to any server. You explicitly create it with a channel that points to a specific host:port. Change the channel, and the same stub points to a different server.
4
The server does not auto-discover your implementation. You must call add_YourServiceServicer_to_server(YourImpl(), server). This registers a method routing table: path → your function.
5
The HTTP/2 path baked into every request is the routing key. When the stub sends a call, the path is /package.ServiceName/MethodName. The server does a dictionary lookup on this path to find the right handler.
6
gRPC does not do service discovery. It is the consumer's responsibility to know the host:port. gRPC provides extension points (name resolvers, load balancers) but does not ship with a built-in service registry.
7
Serialization is Protocol Buffers (protobuf), not JSON. Protobuf encodes data as binary using field numbers (integers), not field names (strings). This makes it 3–10× smaller and faster than JSON.
8
HTTP/2 is the transport, not HTTP/1.1. HTTP/2 supports multiplexing (multiple streams over one TCP connection), header compression (HPACK), and bidirectional streaming — all critical for gRPC's streaming and performance story.
9
The .proto file is the source of truth for both sides. Since stub and servicer base are generated from the same .proto, they are always in sync. If you change the proto and regenerate, both client and server see the same interface.
10
Your servicer implementation is just a Python class. It extends the generated base class and overrides methods. Each method receives a deserialized request object and a context (for metadata, cancellation, deadlines).

Core Components

What each file and class actually contains

pb2.py — Generated Message File

Contains generated Python classes for each message in your .proto. Wraps the protobuf C extension for fast serialization.

# What protoc generates in pizza_pb2.py
# You never write this — only read it to know available fields

class PizzaOrder(Message):
    size: str             # field 1 → encoded as tag 0x0A
    toppings: List[str]  # field 2 → encoded as tag 0x12
    address: str          # field 3 → encoded as tag 0x1A

# Usage: create a message
order = pizza_pb2.PizzaOrder(size="large", toppings=["cheese"], address="123 Main")
# Serialize to bytes
raw = order.SerializeToString()   # → b'\x08\x03\x12\x06cheese...'
# Deserialize from bytes
recovered = pizza_pb2.PizzaOrder.FromString(raw)

pb2_grpc.py — Generated gRPC Plumbing

Contains three things: the Stub class (client), the Servicer base class (server interface), and the registration function.

# What protoc generates in pizza_pb2_grpc.py

# 1. SERVER BASE CLASS — you extend this
class PizzaServiceServicer:
    def TakeOrder(self, request, context):
        context.set_code(grpc.StatusCode.UNIMPLEMENTED)
        raise NotImplementedError

    def CheckStatus(self, request, context):
        context.set_code(grpc.StatusCode.UNIMPLEMENTED)
        raise NotImplementedError

# 2. CLIENT STUB — you instantiate this with a channel
class PizzaServiceStub:
    def __init__(self, channel):
        self.TakeOrder = channel.unary_unary(
            '/pizza.PizzaService/TakeOrder',   # ← HTTP/2 path
            request_serializer=pizza_pb2.PizzaOrder.SerializeToString,
            response_deserializer=pizza_pb2.OrderConfirmation.FromString,
        )

# 3. REGISTRATION FUNCTION — call this on server startup
def add_PizzaServiceServicer_to_server(servicer, server):
    # Builds a routing dict and registers it with the gRPC server core
    server.add_generic_rpc_handlers([
        GenericMethodHandler('/pizza.PizzaService/TakeOrder' → servicer.TakeOrder),
        GenericMethodHandler('/pizza.PizzaService/CheckStatus' → servicer.CheckStatus),
    ])

Your Implementation (what you actually write)

# YOUR CODE — server side
class MyPizzaService(PizzaServiceServicer):   # extend the generated base
    def TakeOrder(self, request, context):
        # request is a fully deserialized PizzaOrder Python object
        order_id = db.save_order(request.size, request.toppings, request.address)
        return pizza_pb2.OrderConfirmation(order_id=order_id, eta_minutes=30)

# Start server
server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
add_PizzaServiceServicer_to_server(MyPizzaService(), server)
server.add_insecure_port('0.0.0.0:50051')
server.start()

# ─────────────────────────────────────────────────────
# YOUR CODE — client side
channel = grpc.insecure_channel('pizza-server:50051')  # YOU provide the address
stub = PizzaServiceStub(channel)
confirmation = stub.TakeOrder(pizza_pb2.PizzaOrder(
    size="large", toppings=["cheese", "mushroom"], address="123 Main"
))
print(confirmation.order_id)  # back to Python land

Service Discovery — Who Tells the Consumer?

How clients learn about host:port — gRPC's responsibility boundary
The core truth: gRPC does NOT do service discovery. The consumer must know the address. gRPC provides hooks to plug in a name resolver, but ships with no built-in registry. This is a deliberate design separation of concerns.
Pattern 1

Hardcoded / Env Var

Simplest approach. PIZZA_SERVICE_ADDR=pizza-server:50051 in environment. Works fine for small setups, breaks at scale (can't update without redeploy).

import os
addr = os.getenv("PIZZA_ADDR", "localhost:50051")
channel = grpc.insecure_channel(addr)
Pattern 2

DNS

In Kubernetes, every Service gets a DNS name. Consumer uses the DNS name as the channel address. DNS returns one or more IPs (for load balancing). gRPC's built-in DNS resolver handles this natively.

channel = grpc.insecure_channel(
  "dns:///pizza-svc.prod.svc.cluster.local:50051"
)
Pattern 3

Service Registry

Server registers itself on startup (Consul, etcd, ZooKeeper). Consumer queries registry at startup (or periodically) to get the current address. Allows zero-downtime migrations and autoscaling.

# Server side on startup
consul.register("pizza-service", host=my_ip, port=50051)

# Consumer side
addr = consul.lookup("pizza-service")
channel = grpc.insecure_channel(addr)
Pattern 4

Load Balancer

Consumer always hits a fixed LB address. LB routes to healthy backend instances. Consumer needs no awareness of actual server IPs. Used in production cloud deployments (AWS ALB, GCP Load Balancer, Envoy).

# Consumer only knows the LB address
channel = grpc.insecure_channel("grpc-lb.internal:50051")
# LB figures out which pizza server to use

Server-Side Registration — How Methods Get Wired

Once the consumer connects to the right host:port, the server's internal routing table dispatches to the right method. This table is built during add_..._to_server():

# What add_PizzaServiceServicer_to_server() builds internally:
routing_table = {
    "/pizza.PizzaService/TakeOrder":   {
        "handler": my_servicer.TakeOrder,
        "request_deserializer": pizza_pb2.PizzaOrder.FromString,
        "response_serializer": pizza_pb2.OrderConfirmation.SerializeToString,
    },
    "/pizza.PizzaService/CheckStatus": {
        "handler": my_servicer.CheckStatus,
        # ...
    },
}
# On every incoming request: path → handler → deserialize → run → serialize → send

Routing Internals

How gRPC knows exactly which Python function to call

The Path Convention

Every gRPC call is an HTTP/2 POST. The path is deterministic:

/package.ServiceName/MethodName

# Example from pizza.proto:
# package pizza;
# service PizzaService { rpc TakeOrder(...) ... }

/pizza.PizzaService/TakeOrder
/pizza.PizzaService/CheckStatus

This path is hardcoded into the generated Stub during code generation. You never write it manually.

Multiple Services on One Port

Since routing uses the full service name path, you can register multiple services on the same server:

server = grpc.server(executor)

# Multiple servicers on one port — no conflict
add_PizzaServiceServicer_to_server(PizzaImpl(), server)
add_DrinkServiceServicer_to_server(DrinkImpl(), server)
add_PaymentServiceServicer_to_server(PaymentImpl(), server)

server.add_insecure_port('0.0.0.0:50051')
# Routes: /pizza.../  /drink.../  /payment.../

The context Object — What It Gives You

Your Servicer method receives (self, request, context). The context carries the call's metadata and control knobs:

def TakeOrder(self, request, context):
    # Read caller metadata (like HTTP headers)
    auth_token = dict(context.invocation_metadata()).get('authorization')

    # Check if caller cancelled
    if context.is_active() == False:
        return

    # Set error code if something is wrong
    if not is_authorized(auth_token):
        context.set_code(grpc.StatusCode.PERMISSION_DENIED)
        context.set_details("Invalid token")
        return pizza_pb2.OrderConfirmation()  # empty response

    # Check deadline (timeout passed by caller)
    deadline = context.time_remaining()  # seconds left before timeout

    return pizza_pb2.OrderConfirmation(order_id="abc-123")

Deep Technical Aspects

Wire format, HTTP/2 internals, protobuf encoding, and performance details

Protobuf Wire Format

  • Each field encoded as (field_number << 3 | wire_type) + value
  • Strings: varint length prefix + UTF-8 bytes
  • Integers: variable-length encoding (1–10 bytes)
  • No field names on the wire — only field numbers (integers)
  • Unknown fields are preserved (forward compatibility)
  • Default values omitted entirely (zero = not present on wire)
  • ~3–10× smaller than equivalent JSON

HTTP/2 Transport

  • Single TCP connection, multiple logical streams (multiplexing)
  • Each gRPC call is one HTTP/2 stream (stream ID)
  • Headers compressed with HPACK (saves repeated metadata)
  • DATA frames carry the protobuf payload
  • 5-byte gRPC framing header: 1 compression flag + 4 byte length
  • TRAILERS carry gRPC status code and error details
  • Supports client/server/bidi streaming natively

Channel Internals

  • Channel is a logical connection to a server (not one TCP socket)
  • Backed by a connection pool, lazily connected on first call
  • Handles reconnection with exponential backoff automatically
  • Supports subchannel list for client-side load balancing
  • Name resolver plugin converts addresses to IPs/subchannels
  • Channels are thread-safe and should be reused (expensive to create)

Interceptors (Middleware)

  • gRPC supports interceptors on both client and server
  • Client interceptors: auth token injection, retry logic, tracing
  • Server interceptors: auth validation, logging, rate limiting
  • Executed in a chain before/after the actual method call
  • Access to full request, response, and context objects
  • Used to implement cross-cutting concerns without touching servicer code

Streaming Modes

  • Unary: one request, one response (most common)
  • Server streaming: one request, stream of responses
  • Client streaming: stream of requests, one response
  • Bidirectional streaming: both sides stream simultaneously
  • All modes use the same HTTP/2 stream; framing differentiates them
  • Streaming methods get an iterator/generator interface in Python

Error Model

  • gRPC has 16 canonical status codes (OK, NOT_FOUND, UNAVAILABLE, etc.)
  • Set via context.set_code() + context.set_details() in the servicer
  • Client receives grpc.RpcError exception with .code() and .details()
  • Rich errors possible via google.rpc.Status protobuf (error details)
  • Deadlines propagate automatically — server can check time_remaining()
  • Cancellation propagates: if client cancels, context.is_active() → False

Thread Model (Python)

  • grpc.server() takes a ThreadPoolExecutor — each call gets a thread
  • Default max_workers=None → unbounded (dangerous under load)
  • For async: use grpc.aio.server() with asyncio event loop
  • Context.run_in_executor() for CPU-bound work from async servicer
  • The GIL limits true CPU parallelism; I/O-bound work is fine

Reflection & Health Checks

  • gRPC Server Reflection: register service definitions at runtime
  • Tools like grpcurl and Postman use reflection to discover methods
  • gRPC Health Checking Protocol: standard HealthCheck service
  • Load balancers use health checks to drain unhealthy instances
  • Both are additional servicers you register — not built-in

Frequently Asked Questions

Common questions answered concisely — click to expand
Q   Do I ever edit pb2.py or pb2_grpc.py files manually? ▼
Never. Both files are auto-generated by protoc (the Protocol Buffer compiler) and will be overwritten the next time you run code generation. Your changes would be lost. Treat them as build artifacts. You read pb2.py to know which message classes are available, but you never write to it.
Q   How does gRPC know which server to call? Does it do service discovery? ▼
gRPC does NOT do service discovery. This is a deliberate design decision. The consumer must supply the host:port when creating the channel. In production, the address typically comes from: (1) environment variables, (2) DNS — especially in Kubernetes where services have DNS names, (3) a service registry like Consul or etcd, or (4) a load balancer address. gRPC provides a name resolver plugin interface if you want to integrate with a custom registry.
Q   What is the difference between the Stub and the Servicer? ▼
The Stub lives on the consumer/client side. It is a thin wrapper that sends method calls over the network. The Servicer base class lives on the server side and defines the interface your implementation must satisfy (all methods raise NotImplementedError by default). You never use the base Servicer directly — you subclass it and implement the methods. Both are generated from the same .proto file so they always agree on method signatures.
Q   Can I run multiple gRPC services on the same port? ▼
Yes. gRPC routing uses the full HTTP/2 path which includes the service name (e.g., /pizza.PizzaService/TakeOrder vs /drinks.DrinkService/OrderDrink). You simply call add_..._to_server() for each service on the same server instance before starting it. They share the port but are routed independently.
Q   What is the context parameter in the Servicer method? ▼
The context object represents the current RPC call. It gives you: (1) metadata — key-value pairs sent by the caller (like HTTP headers), (2) deadlines — how much time is left before the call times out, (3) cancellation — whether the caller has cancelled the call, and (4) status control — ability to set the gRPC status code and error details on the response. Think of it as the HTTP request/response context equivalent for gRPC.
Q   Why is protobuf binary instead of JSON? Isn't JSON easier? ▼
JSON is text-based: field names are strings repeated in every message, numbers are human-readable characters, no schema enforcement. Protobuf is binary: field names are replaced with small integers (field numbers), values are compactly encoded, and the schema (defined in .proto) is separate from the data. The result is ~3–10× smaller payloads and faster parsing. The tradeoff: you can't just curl a gRPC endpoint and read the response — you need the schema to decode it.
Q   What happens if the consumer sends the wrong message type? ▼
If you're using generated stubs (pb2_grpc), this can't happen at compile time — the stub's method signature only accepts the correct type. At runtime, if bytes arrive that don't match the expected proto schema, deserialization may produce a partially-filled message (unknown fields are dropped by default) or raise a decode error. This is why keeping your .proto file as the shared source of truth and regenerating both sides together is essential.
Q   Can I use gRPC from a browser? ▼
Not directly. Browsers don't support HTTP/2 trailers (which gRPC uses for status codes). You need a grpc-web proxy (like Envoy) in front of your gRPC server. grpc-web translates between the browser's HTTP/1.1 or fetch-based requests and the real gRPC protocol. Alternatively, some teams expose a REST/JSON transcoding layer on top of gRPC for external/browser consumers, while keeping gRPC for internal service-to-service calls.
Q   How do I debug gRPC calls? I can't just use curl. ▼
Several options: (1) grpcurl — command-line curl for gRPC, works with server reflection enabled, (2) Postman — has built-in gRPC support with reflection, (3) Evans — interactive gRPC client, (4) enable gRPC verbose logging with GRPC_VERBOSITY=DEBUG GRPC_TRACE=all environment variables, (5) add a server interceptor that logs every request. Enable server reflection with from grpc_reflection.v1alpha import reflection to allow tools to auto-discover your service methods.
Q   What is the relationship between the .proto file and the generated files? ▼
The .proto file is the authoritative human-written contract. You run python -m grpc_tools.protoc (or the standalone protoc binary) to generate both pb2.py and pb2_grpc.py from it. The generated files should be committed to your repo (or generated as part of your build). If you change the .proto file, you must regenerate. In a polyglot system (Python server, Go client), each language generates its own pb2/pb2_grpc equivalents from the same .proto — this is how they stay in sync across languages.
