Simple Introduction

What MCP is, why it exists, who runs what

MCP (Model Context Protocol) is an open standard introduced by Anthropic in November 2024 that lets AI applications — chat clients, IDEs, agents — plug into external tools and data through a single uniform protocol. Instead of every AI app shipping a custom Slack integration, custom GitHub integration, custom database integration, each tool author publishes one MCP server, and any MCP-aware host can use it.

Concretely: an MCP host (Claude Desktop, Claude Code, Cursor, Zed, Continue, …) spawns one or more clients, each of which speaks JSON-RPC 2.0 to a server. The server exposes three kinds of capabilities: tools the model can call, resources the app can attach to context, and prompts the user can invoke as templates.

The Problem

Before MCP, integrating N AI apps with M tools needed N×M bespoke adapters. Every vendor reinvented connector frameworks, function-calling schemas, and auth flows. Tool authors had to publish to many walled gardens; AI apps had to maintain dozens of one-off connectors.

The Solution

MCP defines one protocol with a standard handshake, capability negotiation, and three primitives. Tool authors write one server; AI app vendors write one client. N+M instead of N×M. Bonus: the user controls which servers their host connects to — security and consent live with the host, not the tool.

One-Liners

Host = the AI app. Client = a 1:1 connection inside the host. Server = the integration. Tool = a function the model can call. Resource = data the app can read. Prompt = a templated user-invoked instruction. Transport = how bytes move (stdio or Streamable HTTP).

Key insight: MCP is not an LLM API. It does not call models. It is a protocol between an AI app and an external integration, sitting at the layer where the app would otherwise hard-code a Slack or GitHub adapter. The model itself never speaks MCP — the host translates between MCP and whichever LLM API it uses (Claude, OpenAI, local).

The USB-C Analogy

Mapping MCP roles to a peripheral hub

Think of your laptop's USB-C hub. The laptop doesn't care whether the thing on the other end is a monitor, a microphone, or a hard drive — it just speaks USB-C. Each peripheral implements the same protocol, advertises what it can do, and the laptop wires it in. MCP is exactly this, but for AI apps and external integrations.

Technical Concept

Host (AI app)
The laptop. Owns user identity, the screen, and consent. Decides which peripherals are allowed to plug in.
🔌

Technical Concept

Client
A single USB-C port on the laptop. There's exactly one client per peripheral (1:1 connection), and the laptop manages many ports in parallel.
🖱️

Technical Concept

Server
A peripheral — mouse, keyboard, drive. Plugs in, announces what it can do ("I'm a 1080p webcam"), and responds to requests.
📡

Technical Concept

Transport
The physical cable. stdio = the cable goes to a peripheral inside the same case (subprocess). HTTP = the cable goes over the network to a remote device.
📋

Technical Concept

Capability Negotiation
USB device descriptors. On plug-in, the peripheral lists what it supports ("I have a microphone, a camera, and a button"). The host only enables features both sides understand.
🔧

Technical Concept

Tools / Resources / Prompts
Three kinds of "device classes." A USB drive (resource — read data), a printer (tool — perform an action), a macro keyboard (prompt — preset user-triggered command).
Analogy flow: You plug a server into the host (configure it in ~/.claude.json or equivalent). The host's client opens a "port" and runs initialize. The server replies with its capability descriptor. The host wires the discovered tools into the model's tool list. When the model calls one, the request travels down the cable, the server executes, and the result comes back as JSON-RPC.

Key Statements

The most important truths, one at a time
1
MCP is a protocol, not a runtime. It defines messages on a wire — there is no SDK lock-in. You can implement an MCP server in any language that can read stdin and write JSON.
2
Every MCP message is JSON-RPC 2.0. Three message types only: request (expects response), response (matches a request id), and notification (fire-and-forget, no id).
3
The host controls consent, not the server. The server can offer tools; the host decides which the model is allowed to see and whether to confirm with the user before each call.
4
One client = one server. If your host connects to 10 servers, it has 10 clients. Each is a separate JSON-RPC session with its own state and capabilities.
5
Three primitives, three controllers. Tools are model-controlled (the LLM decides when), resources are app-controlled (the host decides what to attach), prompts are user-controlled (a human picks them from a menu).
6
Discovery is dynamic. A server can announce listChanged and push notifications/tools/list_changed at any time — the client re-fetches and the new tool becomes available mid-session.
7
Servers can call clients back. Via sampling a server can ask the host to run an LLM completion on its behalf. Via elicitation it can request structured input from the user. Via roots it learns which paths it's allowed to touch.
8
stdio is for local, Streamable HTTP is for remote. The old "HTTP+SSE" two-endpoint transport from the original spec was replaced in 2025 by a single-endpoint Streamable HTTP transport.
9
Auth is OAuth 2.1 for remote servers. The 2025 spec mandates OAuth 2.1 with PKCE for HTTP transports. Local stdio servers typically read API keys from environment variables set by the host config.
10
The model never sees MCP wire bytes. The host translates: it converts MCP tools/list output into the LLM provider's tool schema, and converts the LLM's tool-call request back into MCP tools/call.

Core Components

The pieces of any MCP system, with concrete code

1. The Server — exposes capabilities

A server is a process that owns some external resource (filesystem, GitHub, database) and translates JSON-RPC requests into operations on that resource. Below: a minimal Python server using the official SDK that exposes one tool.

# server.py — runs as a subprocess, communicates over stdio
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_forecast(city: str, days: int = 3) -> str:
    """Return a weather forecast for the given city."""
    # … real impl would call a weather API …
    return f"Forecast for {city} for next {days} days: sunny."

if __name__ == "__main__":
    mcp.run(transport="stdio")

2. The Host config — wires servers in

The host (Claude Desktop here) reads a JSON config that tells it how to spawn each server. The host launches the command, pipes stdin/stdout, and from then on talks JSON-RPC to it.

// ~/Library/Application Support/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "weather": {
      "command": "python",
      "args": ["/Users/me/servers/weather/server.py"],
      "env": { "WEATHER_API_KEY": "sk-…" }
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "ghp_…" }
    }
  }
}

3. The Client — what the host runs internally

When the host starts the server subprocess, it instantiates a client object that owns the JSON-RPC session. Most hosts use the official TypeScript or Python SDK rather than rolling their own.

import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const transport = new StdioClientTransport({
  command: "python",
  args:    ["/Users/me/servers/weather/server.py"],
});

const client = new Client({ name: "my-host", version: "1.0.0" });
await client.connect(transport);          // initialize handshake

const { tools } = await client.listTools();
const result   = await client.callTool({
  name: "get_forecast",
  arguments: { city: "Paris", days: 5 },
});

4. The wire — JSON-RPC 2.0 over the transport

Every interaction is a JSON-RPC envelope. The client sends a request, the server replies with a response carrying the same id. Notifications have no id and need no reply.

// Client → Server
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "get_forecast",
    "arguments": { "city": "Paris", "days": 5 }
  }
}

// Server → Client
{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "content": [{ "type": "text", "text": "Forecast for Paris…" }],
    "isError": false
  }
}

5. The model bridge — translating MCP to LLM tool calls

The host turns each MCP tool into a function entry on its LLM API call. When the model emits a tool-use block, the host routes it to the right MCP client by tool name.

# Host pseudocode — translating MCP to Anthropic tools API
mcp_tools = await client.list_tools()  # MCP shape

anthropic_tools = [
  {
    "name":        t.name,
    "description": t.description,
    "input_schema": t.inputSchema,  # JSON Schema, same shape
  } for t in mcp_tools
]

response = anthropic.messages.create(
    model="claude-opus-4-7",
    tools=anthropic_tools,
    messages=[{"role": "user", "content": "forecast Paris"}],
)

for block in response.content:
    if block.type == "tool_use":
        result = await client.call_tool(block.name, block.input)
        # … feed result back to model …

Transports & Configuration

stdio vs Streamable HTTP, how messages actually move
Core truth: MCP is transport-agnostic at the message level — JSON-RPC envelopes don't change. The transport just decides how envelope bytes get from one process to another. Two transports are standard: stdio for local subprocess servers, Streamable HTTP for remote/network servers.
Transport 1

stdio

Server is launched as a subprocess of the host. Messages = JSON lines on stdout/stdin. Stderr is reserved for logs. Zero network exposure, zero auth — trust comes from the host having spawned the binary.

# Newline-delimited JSON-RPC over pipes
{"jsonrpc":"2.0","id":1,"method":"initialize",...}
{"jsonrpc":"2.0","id":1,"result":{...}}
Transport 2

Streamable HTTP

Single HTTP endpoint (e.g., /mcp). Client POSTs requests, server replies inline OR upgrades to SSE for streaming responses + server-pushed notifications. Replaces the old two-endpoint HTTP+SSE transport.

POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream

{"jsonrpc":"2.0","id":1,...}
Capability declaration

Negotiated at init

Each side advertises a capabilities object during initialize. Servers declare tools, resources, prompts, logging; clients declare sampling, roots, elicitation. Features absent from either side are off.

{
  "capabilities": {
    "tools": { "listChanged": true },
    "resources": { "subscribe": true }
  }
}
Versioning

Date-string protocol versions

Versions are date strings like 2025-06-18. Client proposes a version; server returns the version it'll use (may downgrade). Mismatch ⇒ client must disconnect. The spec is a living document — current version is published at modelcontextprotocol.io/specification.

A complete initialize exchange

The handshake declares versions and capabilities. Once the notifications/initialized note is sent, both sides may use any negotiated feature.

// 1. Client → Server
{
  "jsonrpc": "2.0", "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "sampling": {},
      "roots": { "listChanged": true }
    },
    "clientInfo": { "name": "claude-desktop", "version": "0.10.0" }
  }
}

// 2. Server → Client
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": {},
      "prompts": {}
    },
    "serverInfo": { "name": "weather-server", "version": "1.0.0" }
  }
}

// 3. Client → Server (notification, no id, no response)
{ "jsonrpc": "2.0", "method": "notifications/initialized" }

Dispatch & Routing

How a tool call from the model finds the right server, and the right function inside it

Tool name → server

The host maintains a name→client map built from tools/list responses. When the LLM calls tool get_forecast, the host looks up which client owns that name and routes the JSON-RPC there.

# Host-side dispatch table
tool_to_client = {}
for server_name, client in active_clients.items():
    for tool in await client.list_tools():
        tool_to_client[tool.name] = client

# When model emits tool_use:
client = tool_to_client[block.name]
result = await client.call_tool(block.name, block.input)

Name collisions across servers

Two servers can both expose a tool named search. Hosts disambiguate by namespacing — Claude Code prefixes tool names with mcp__<serverName>__<toolName> when sending to the LLM. The server itself never sees the prefix.

# What the model actually sees
[
  "mcp__github__search",
  "mcp__filesystem__search",
  "mcp__weather__get_forecast",
]

# Host strips the prefix before tools/call
server, name = block.name.removeprefix("mcp__").split("__", 1)
await clients[server].call_tool(name, block.input)

Inside the server: method → handler

Within a server, JSON-RPC method strings dispatch to handlers via a registry. The SDK does this for you — decorate a function and it's auto-registered for both tools/list and tools/call.

# FastMCP internals (simplified)
class FastMCP:
    def __init__(self, name):
        self._tools: dict[str, Tool] = {}

    def tool(self):
        def decorator(fn):
            self._tools[fn.__name__] = Tool.from_function(fn)
            return fn
        return decorator

    # Handles incoming tools/call
    async def _handle_call_tool(self, params):
        tool = self._tools[params["name"]]
        result = await tool.run(params["arguments"])
        return { "content": [{ "type": "text", "text": str(result) }] }

Resources use URI templates, not function names

For resources, dispatch is by URI. Servers register URI templates (RFC 6570); on resources/read the server matches the requested URI against its templates and calls the matching handler.

@mcp.resource("file:///{path}")
async def read_file(path: str) -> str:
    return Path(path).read_text()

@mcp.resource("postgres://db/{schema}/{table}")
async def read_table(schema: str, table: str) -> str:
    return await db.describe(schema, table)

Deep Technical Aspects

Wire format, threading, errors, security, performance

Wire format details

  • JSON-RPC 2.0 — jsonrpc: "2.0" required on every message
  • stdio uses newline-delimited JSON; one envelope per line, no embedded newlines
  • Streamable HTTP responses may be application/json or text/event-stream
  • SSE event data carries the same JSON-RPC envelope, one per data: field
  • UTF-8 only; binary content (images, audio) is base64-encoded inside content blocks
  • No size limit in the spec — practical limit is the host/server memory and any HTTP gateway in between

Concurrency & request IDs

  • Requests are async — multiple in flight simultaneously, matched by id
  • IDs must be unique within a session; SDKs use monotonically increasing integers
  • Notifications have no id and never get a response
  • Order is not guaranteed — request 5 may complete before request 3
  • Servers may process requests in parallel or serially; the protocol doesn't mandate one
  • Cancellation via notifications/cancelled with the request's id

Error model

  • Two error layers: protocol errors (JSON-RPC error object with code/message) and tool errors (200-OK result with isError: true)
  • Tool errors carry text content — model can read and recover (e.g., retry with different args)
  • Protocol error codes follow JSON-RPC: -32700 parse, -32600 invalid request, -32601 method not found, -32602 invalid params, -32603 internal
  • Custom server errors use codes ≤ -32000
  • Connection-level errors (broken pipe, HTTP 500) terminate the session
  • SDKs surface tool errors as Python/JS exceptions on the client side

Authorization (HTTP transport)

  • 2025-06-18 spec mandates OAuth 2.1 with PKCE for all HTTP transports
  • Server publishes a metadata document at /.well-known/oauth-authorization-server
  • Dynamic Client Registration (RFC 7591) lets clients register on the fly
  • Access tokens carried in Authorization: Bearer header on every request
  • Refresh tokens supported; token rotation per RFC 6749 §6
  • stdio transport has no auth — trust comes from the host having permission to spawn the subprocess

Sampling (server → host LLM)

  • Server can request the host to run an LLM completion via sampling/createMessage
  • Lets a server be "agentic" without bundling a model or API key
  • Host decides which model to use; server suggests via modelPreferences
  • User must consent (host UI prompts) — server cannot silently bill the user's account
  • Useful for: summarization tools, multi-step planning servers, language translation servers
  • Optional capability — server must declare it during initialize

Roots (host → server scope)

  • Client tells server which URIs it's allowed to operate on (e.g., a list of project directories)
  • Server queries via roots/list; receives roots/list_changed notifications
  • A filesystem server uses roots to refuse reads outside the user's chosen folders
  • Soft contract — enforcement is server-side; a malicious server could ignore them
  • Crucial for sandboxed agents that work on a specific repo
  • Optional capability declared by client

Notifications & subscriptions

  • notifications/tools/list_changed — server's tool catalog updated, re-list
  • notifications/resources/list_changed — same for resources
  • notifications/resources/updated — a specific resource changed (sent only to subscribers)
  • notifications/progress — long-running tool call progress (with optional total)
  • notifications/cancelled — request cancelled by either side
  • notifications/message — server log message at a level (debug/info/warn/error)

Security considerations

  • Prompt injection via tool output — tool result text is fed to the LLM; malicious server can hijack the agent
  • Tool description poisoning — descriptions go in the model's context; misleading text can cause wrong tool selection
  • Confused deputy — server holds a token with broad scope; LLM persuades it to do unintended actions
  • Mitigation: per-call user consent, allowlists, scope-narrowed tokens per server, output scrubbing
  • Spec's Security Best Practices doc enumerates known threats
  • Audit: log every tools/call request and result; many hosts ship this by default

Frequently Asked Questions

Common questions — click to expand
Q   Is MCP an Anthropic-only protocol? ▼
No. Anthropic created and open-sourced it (Apache 2.0), but it's a vendor-neutral spec governed at modelcontextprotocol.io. OpenAI, Google, and others have either adopted it or expressed support. The protocol does not assume Claude — any LLM can sit behind a host.
Q   Does the LLM speak MCP directly? ▼
No. The host sits between them. The host translates MCP tools/list output into the LLM provider's tool schema and converts the LLM's tool-call requests back into MCP tools/call. The model just sees a normal list of tools.
Q   What's the difference between a tool, a resource, and a prompt? ▼
Tool = a function the LLM can decide to call (model-controlled). Resource = data the host can attach to context like a file or DB row (app-controlled). Prompt = a templated user-triggered command, usually surfaced as a slash command (user-controlled). Same protocol, different control point.
Q   How do I write an MCP server? ▼
The lowest-friction path: install the official SDK in Python (pip install mcp) or TypeScript (npm i @modelcontextprotocol/sdk), import FastMCP, decorate functions with @mcp.tool(), and call mcp.run(). For non-SDK languages, implement the JSON-RPC handshake yourself — the spec is small.
Q   How do I add an MCP server to Claude Desktop / Claude Code? ▼
Edit the host's config file. Claude Desktop: ~/Library/Application Support/Claude/claude_desktop_config.json. Claude Code: claude mcp add <name> <command> (CLI) or edit ~/.claude.json. Add an entry under mcpServers with command, args, and optional env. Restart the host.
Q   Can MCP servers run remotely? ▼
Yes — that's the Streamable HTTP transport. The server hosts a single endpoint, the host POSTs JSON-RPC, and the server may upgrade the response to SSE for streaming. Remote servers must implement OAuth 2.1 per the 2025-06-18 spec.
Q   What happens when a tool takes 30 seconds? ▼
Two options. (1) The server can stream notifications/progress messages with a percentage. (2) The host or client can issue notifications/cancelled if the user gives up. The model itself just sees a delayed result; if the host has a timeout, it surfaces an error to the LLM.
Q   Can a server access another server? ▼
Not directly — clients are 1:1 with servers, and servers don't talk to other servers. To compose, you either let the model orchestrate (it calls server A, then B, then C) or build a "meta-server" that internally embeds clients to other servers. The protocol does not gateway between servers.
Q   Is MCP a replacement for OpenAPI / GraphQL / gRPC? ▼
No — different layer. OpenAPI/gRPC describe a service for human-or-machine consumption. MCP describes a service to an LLM, with primitives (resources, prompts) and conventions (capability negotiation, sampling, roots) tuned for that purpose. You can wrap an OpenAPI service as an MCP server in a few hundred lines.
Q   What are the biggest pitfalls in practice? ▼
(1) Vague tool descriptions → model picks the wrong tool. Be specific. (2) Returning huge results → blows the context window; paginate or truncate. (3) Trusting tool output blindly → prompt injection from external data. (4) Stateful tools that assume single-threaded calls — clients can issue parallel requests. (5) Forgetting that env vars on the host config don't reach remote HTTP servers — those need OAuth or their own auth.
